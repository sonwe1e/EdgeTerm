# 找到上轮那条浏览器用例失败的根因（2026-11-24 第 110 轮）

第 109 轮我把一条「真实 App 里按端口找到会话」的用例撤掉了，理由是查 `2222` 时选项为空、根因未定。这一轮把它查清并补回证据。

## 一、根因：状态被后端加载覆盖

夹具在 `mount` **之前**写入 2222 端口的会话，但 App 挂载后会调用 `list_profiles` 并用自己的结果覆盖 store——而那台机器在夹具里是 22 端口。搜索查的其实是旧数据。把写入挪到挂载并等待两帧之后，用例一次通过。

## 二、定位手法：哨兵断言

把断言故意写成不可能命中的字符串，让失败消息携带真实内容：

| 断言 | 失败消息 | 结论 |
| --- | --- | --- |
| 挂载前写入 | `expected 'EscNo command matches "2222"…' to contain 'SENTINEL-TEXT'` | 确实没有匹配，排除了选择器写错 |
| 挂载后写入 | `expected 'EscSaved sessionsConnect to Build ser…'` | 已找到，剩下的只是把它写成正式断言 |

## 三、正式断言 + 负控制

```
expect(rows.join(" | ")).toContain("Build server")   // 列表里唯一含 2222 的是提示
```

去掉 App 里拼接端口的逻辑后，该用例失败（`expected '' to contain 'Build server'`）；恢复后 4/4 通过、typecheck 退出码 0。

## 四、验证

| 层次 | 证据 |
| --- | --- |
| 真实 App | `commandPalette.browser.test.ts` 4/4（新增 1 条） |
| 负控制 | 去掉端口拼接 → 失败；恢复 → 通过 |
| 全量 | 见 STATE 本轮记录 |

## 五、教训

「设置状态再挂载」在本项目的 App 级夹具里**不可靠**：启动过程会用后端数据覆盖 store。夹具要么改后端桩的返回值，要么在挂载之后再设置。
