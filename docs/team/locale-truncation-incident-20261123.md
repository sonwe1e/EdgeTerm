# 一次真实的破坏与恢复：语言包被截断（2026-11-23 第 51 轮）

本轮原本只做两件小事（中键关闭标签、标签栏右键「重新打开已关闭的标签页」）。中途我自己把 `src/locales/en.ts` 与 `zhCN.ts` **截短了约 570 条**，两份语言包都不能编译。这里如实记录：怎么坏的、怎么恢复的、以后怎么防。

## 一、怎么坏的

为了加一个键，我读取整个语言包、改字符串、再整体写回：

```
const cur = await read(file);            // 读取被截断：只返回了前一部分行
const body = cur.lines.map(...).join();  // 于是拼出的正文少了尾部
await write(file, body + newKey);        // 整体覆盖，尾部彻底丢失
```

`read` 的返回带有总行数与实际返回行数，我没有核对就直接整体覆盖。**文件越大，这种读-改-写越危险**；语言包当时约 80 KB。损坏后的报错是 `'}' expected`：文件在最后一条键处结束，缺少收尾。

## 二、为什么能恢复

第 50 轮被取消的 1.8.0 构建留下了 `dist/`（18:41 生成，比损坏早约 9 分钟）。前端打包把两份语言包编进了 `dist/assets/index-*.js`，键与文本以字面量形式存在。恢复步骤：

1. 从 bundle 中提取所有 `"key": "value"` 字面量（2956 对），按键名去重；
2. 含中日韩字符的值归入中文包，其余归入英文包；
3. 与损坏文件中仍存在的键合并（保住第 50 轮新加的 6 个键）；
4. 两包互相对齐（缺哪个补哪个），最终各 **1463** 条；
5. 修回 5 条被误判的键：它们的英文值含双引号，在 bundle 里是**单引号**字面量，被第一步的正则漏掉，误从中文包补成了中文（`panel.deleteGroupPrompt`、`panel.groupDeleted`、`sender.updateTitle`、`filer.invalidName`、`filer.alreadyExists`）。

## 三、恢复的验证

- `npm run typecheck`：通过。语言包的键集定义了 `MessageKey`，任何 `t("…")` 用到不存在的键都会编译失败——这是「键齐全」的强证据。
- 全量单测与浏览器契约：见 STATE。浏览器契约里有大量**精确文本**断言（按钮文案、标题、提示），它们通过说明文本没有串行。

## 四、边界与承认

- 恢复的是**内容**，不是原始文件：键的排列顺序与事故前可能不同（顺序无语义，`Catalog` 是字典）；
- 若某个键在 bundle 中既无英文也无中文（不可能：构建来自完整源码），会表现为 typecheck 失败，本轮没有出现；
- 这次损坏是我造成的，不是既有代码的问题；记录在此，避免下次同样做法。

## 五、规则（已写入 DECISIONS 与 LEARNINGS）

1. **大文件不做读-改-写**：加键、加行一律用按位编辑（`edit`）或追加，绝不再整体覆盖。
2. 非要用 `read` 的正文时，先比较 `lines.length` 与 `totalLines`；不一致就是被截断，必须停下。
3. 长构建的产物（`dist/`、`target/`）可以救回源码内容；取消构建前，先想清楚它是不是唯一的副本。
