# 传输中心与隧道中心的可读性审计（2026-11-23 第 32 轮）

积压清单第二项：状态栏两个「列表型」表面——传输中心与隧道中心——从未量过。它们密度高（行、徽标、行内控件、批量操作），正是目标尺寸与裁切最容易出问题的地方。

## 一、覆盖

| 用例 | 断言 |
| --- | --- |
| 传输中心 @900×560，深/浅两主题 | 两个预置作业都在列表里；对比度、目标尺寸、裁切三项采集器全清；逐焦点有无可见焦点样式 |
| 隧道中心 @900×560 | 面板自身三项采集器全清、焦点样式存在；面板有内容而不是空壳 |

传输作业是**真实形状**的种子数据：一个 running（带速率/ETA 字段），一个 failed（带错误消息），因此行内元信息、失败色和批量「Clear failed」条都在测量范围内。

## 二、两处脚手架陷阱（都写进了用例注释）

1. **每个主题重新 mount 会留下两棵 App 树**：第二次点击状态项打开的是旧树的弹层，而断言查的是新树的 DOM，得到 null。改成一个 mount、切换主题后再测。
2. **隧道表单需要活的 SSH 会话**才有输入框；本夹具没有会话，所以断言改成「面板有内容」+「若存在输入框则必须有可访问名」，而不是假定表单存在。

另外把「焦点停顿数 > 1」放宽为 > 0：弹层只有少数几个 Tab 停顿，数字门槛应服从组件结构，而不是反过来。

- `ForwardCenter.tsx`：表单在无会话时不渲染，属于**有意设计**而非缺陷；未改动。

## 四、边界

- 隧道表单（方向单选、监听/目标地址、端口）在无会话时不渲染，**其字段级审计未覆盖**；要覆盖需构造已连接会话，属后续工作。
- 只覆盖 Chromium 与受控 IPC。
