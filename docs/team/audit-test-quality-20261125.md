# 审计：测试套件的回归价值（2026-11-25 第 217 轮）

第 160–216 轮审的都是**产品行为**。这一轮换了个方向：审**测试本身能不能抓住回归**——不是覆盖率，是「删掉断言它还绿不绿」「改坏代码它红不红」。

方法：读完或部分读了 **46 个测试文件及其被测对象**，覆盖前端单测、浏览器测试与全部 7 个 Rust `*_tests.rs` 夹具；另对 **290 个测试文件里 1823 个 `it`/`test` 块**做了一次程序化扫描（零断言块、mock 与 import 相撞、同名测试、只有负断言、快照用量）。

## 明确查过没有问题的两类

**「mock 了正要验的东西」——没有。** 52 个同时 mock 又 import 某模块的文件，mock 的都是 IPC／原生边界（`./api`、`./nativeDialog`、`./bindings`），被测逻辑是真模块。`updater.test.ts` 甚至是刻意的反向操作：拒绝 mock 更新插件，改为对模块源码做断言，并在注释里说明 mock 会让断言变得空洞。

**「快照或 toBeTruthy 能对 almost anything 通过」——没有。** 全仓 **0 个** `toMatchSnapshot`／`toMatchInlineSnapshot`。49 处 `toBeTruthy()` 都带失败消息，且样式探针都是把解析出的值和导出常量比对（`declaredHeight("transfer-job")` 对 `JOB_ROW_HEIGHT`），任一侧变动都会红。

## 审计者自己做的负对照

为免误报，它验证了 `ResourceMonitorBar.test.ts` 的 `styled()` 对真实样式表**确实有判别力**（此前一条审计备注声称它恒为 false——那个函数早已修好）。另确认 24 个「零断言块」是它自己的扫描器被注释里的撇号绊住，23 个其实委托给了带断言的助手函数，只有 T2 是真的。

## 本轮只修了三条

T1、T2、T6 都是小改动且立刻提升判别力。T3、T4、T5 需要删测试或补正向锚点，各自要确认「删掉的是不是真的重复」，本轮预算不足，连精确位置都记在上面。

### T2 修的过程中我错了两次

1. 先按审计建议写 `expect(...directories?.terminal).not.toBe("/late")`——**红**。真相是这个会话仍连着，capture 会重新查询、`/late` 立刻就返回，**它会落盘**。我假设了一个不存在的行为。
2. 改用 `readSavedWorkspace()` 又报 `TS2554`（它收一个 storage 参数），换成文件里已有的 `stored()` 助手后**还是红**：快照是 null，因为 `saveCurrent` 的写入被推迟，而假定时器还没跑到。

最后保留的是**真正有判别力**的那条：`/late` 是否落盘。两次错误都是「凭审计描述下手，没有先读当前代码」——和上一轮 `bytes`／重复键两次自伤同一类。
