# 设置与快捷键对话框：笔记本尺寸下的焦点与可读性（2026-11-23 第 31 轮）

积压清单的第一项是「焦点扫查扩面到设置/快捷键对话框」。它们此前只在 1280×800、单主题下被量过文本对比度、目标尺寸与裁切，**键盘焦点环完全没量**。

## 一、本轮补上的覆盖

| 用例 | 断言 |
| --- | --- |
| 设置对话框 @900×560，深色与浅色 | 对话框完全在视口内；文本对比度 / 目标尺寸 / 裁切三项采集器全清；全对话框逐个焦点停顿都有可见焦点样式；焦点环颜色对比度达标 |
| 快捷键表 @900×560 | 同上（焦点样式 + 焦点环对比度），焦点停顿 > 8 个 |

两条用例都在扫描前**发一次真实 Tab**：`focusRingIssues` 只能对程序化聚焦做诚实判断的前提是键盘模态已经存在，否则 `:focus-visible` 不匹配，所有按钮都会被误报成「聚焦无变化」。

## 二、一个被排除的误报

第一次跑出 10 条 `button.btn | no visible change on keyboard focus`，包括对话框的 Close、Open、Reset、Clear、Restore。核对 `foundation.styles.css` 后确认全局规则存在且正确：

`:where(button, a[href], [role=tab], …):focus-visible { outline: 2px solid var(--accent); outline-offset: -2px; }`

问题在用例：没有先发 Tab，Chromium 不给程序化聚焦的按钮 `:focus-visible`。**这是测试脚手架的缺陷，不是产品缺陷**——所以修的是用例，没有为了让断言变绿去改 CSS。

## 三点五、一次真实的抖动，以及加固

全量套件第一次跑这条用例时失败过一次，单独重跑与随后全量重跑都通过——典型的顺序/时序抖动。可能的原因是测量发生在模态对话框的入场过渡里（松手一帧就看 computed style）。加固两处，都在断言里写明理由：

1. 打开对话框后先等到焦点进入对话框（模态自己的聚焦），不再假设它已经稳定；
2. 三项采集器与焦点扫描**都在冻结动效的状态下测量**（原本只有扫描冻结）。

加固后该文件连跑 3 次全绿，随后全量套件也全绿。
## 三、代码质量评估（本轮被检查的文件）

- `SettingsDialog.tsx`：分组（SettingsGroup）与行（SettingsRow）结构清晰，控件都用既有 `btn`/字段类，未发现需要重构的坏味道；本轮未改动它。
- `dialogAudit.browser.test.ts`：原来缺少焦点环采集器的导入与 `withMotionFrozen` 辅助；本轮补齐并把「先 Tab 再扫」写进注释，避免下一个人重复踩。

## 四、边界

- 只在 Chromium 与受控 IPC 下测量；
- 只覆盖对话框打开后的静态状态（不测滚动到最底部后的每一行，采集器按可见性过滤）；
- `focusRingContrastIssues` 只对 outline 颜色做判定，box-shadow 环计入「不确定」而不判负。
