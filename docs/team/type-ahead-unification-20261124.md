# 两处 type-ahead 合并到同一次搜索（2026-11-24 第 104 轮）

同一个想法在这个项目里出现了两次：文件列表的 `fileTypeSelect.typeToSelect` 和会话树的 `sessionTypeAhead` 都在「按前缀找下一行」。文件列表那份更成熟——NFC 归一、输入法组合判断、重复字母轮转、跨平台键盘。

## 一、做法

| 层 | 处理 |
| --- | --- |
| 匹配核心 | `findByPrefix` 放宽为接受**任何带 `name` 的行**，两处共用；它会做 NFC + 小写归一并环绕 |
| 树的行选择 | `nextTypeAheadRow` 改为委托 `findByPrefix`，删掉自己那份循环 |
| 树的缓冲区 | 补 `isComposing`：输入法组合期间的按键不再被当作 type-ahead |
| 键位语义 | **不合并**：文件列表允许空格续写（空格在那里不承担动作），会话树排除空格（空格是折叠）；两者各自保留 |

这条边界的理由很重要：**共用的是匹配，不是键位策略**。上一轮刚因为「接管空格」踩过坑，这里不再把两种列表的空格含义强行对齐。

## 三、为什么算「质量」而不是「重构癖」

两份前缀搜索意味着两套归一化与边界处理：一份修好 NFC，另一份不会跟着好。合并后，输入法组合与 Unicode 归一这两件事只需在一个地方正确。
