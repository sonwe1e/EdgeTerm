# 那条重流程用例的超时预算（2026-11-24 第 85 轮）

第 84 轮全量浏览器里 `lineSpacing.browser.test.ts` 失败，日志给出的原因不是断言不成立，而是：

```
Error: Test timed out in 15000ms.
```

这条用例要走**三次对话框往返**（每次都用键盘打开命令面板、输入、回车、等对话框出现），中间还夹着终端重排的行数测量。单独跑 8.7 秒，全量并发时跨过 15 秒默认上限——**这是测试装置的上限，不是行为的问题。**

## 一、修正

给这一条用例显式的 30 秒预算（`it(..., 30000)`），并在用例上方写明原因。断言一条没动：行数变多、变少、记忆、gutter 行高都仍按原样检查。

## 二、判断依据

| 证据 | 结论 |
| --- | --- |
| 失败信息是 `Test timed out in 15000ms` | 不是断言失败，也不是产品行为错误 |
| 同一文件单独跑 8.7 秒通过；本轮全量再跑 316/316 通过 | 只有负载下才超时 |
| 用例本身含三次模态往返 | 它本来就是套件里最重的几条之一 |

## 三、没有做的事（如实记录）

- 没有给所有浏览器用例统一放宽超时：那会把「真的很慢」也一起藏起来。
- 没有改动 `until()` 的轮询上限：先只解决已被证据指认的那一条。
- 第 80 轮 `watchWords` 的失败是断言（`expected undefined to be true`），与本轮的超时不同源，仍未复现，保持原记录。
