# 自动聚焦不再抢走「你刚放好的焦点」（2026-11-23 第 43 轮）

本轮验证里 `tabRename.browser.test.ts` 失败一次：F2 没有打开改名框。日志（`.tmp/browser-run-43.log`）给出了完整现场，顺着查到一个**真实的产品缺陷**，而不是测试抖动。

## 一、缺陷

`TerminalPane` 的自动聚焦在 `requestAnimationFrame` 里执行，原守卫只看当前焦点是不是 `input/textarea/select`。于是：

1. 读者（或测试）把焦点放到标签上；
2. 终端在下一帧才挂上/重新可见，自动聚焦按时执行；
3. 焦点从标签被抢到终端——F2 是标签自己的键，落到终端后什么都不发生。

同样的机制也会吃掉落在一个菜单、一个刚出现的按钮上的焦点：凡是在 rAF 之前放好、rAF 之后被抢走的，都会「按键没反应」。这也解释了前几轮里几次**未复现**的浏览器失败：它们的名字不同，机制相同。

## 二、修法

在调度自动聚焦时记下当时的 `document.activeElement`；帧里如果焦点已经**变成别的东西**（且不是 `<body>`），说明读者在这期间主动移动了焦点，自动聚焦让位。

- 没有人在意焦点时（焦点在 body 或仍在终端里），自动聚焦照常工作；
- 点标签切标签后由读者/应用自己决定焦点，不再被一个迟到的帧改写；
- 既有的「字段优先」守卫保留。

## 三、验证

- `tabRename.browser.test.ts` 连跑 3 次全绿（修复前在负载下会失败）；
- 全量浏览器契约 275/275 通过（含这条以前会抖的用例）；
- 该缺陷无法用单测稳定表达（它取决于帧与事件顺序），因此以「同一用例连跑三次 + 全量通过」为证据，并如实说明其概率性。

## 四、边界

- 修复只涉及自动聚焦的**让位条件**，不改变「谁应该在什么时拿到焦点」的其他规则（第 43–46 轮定的提交后聚焦 shell 等）；
- 焦点在 body 时仍会被终端接管：这是首次进入界面的预期行为。
## 六、第 54 轮：它又出现了，根因不是产品，是这条用例的一条前提

第 54 轮的全量浏览器运行再次失败在同一个断言（`F2 starts a rename: expected null not to be null`）。先做的事是测量：单文件连跑 8 次全绿，说明它只在**全量负载**下出现。

### 先试过的修法（已回退）

在 rAF 里加一条「焦点已在终端之外就让位」的守卫。全量浏览器连续两次全绿——但单测 `WorkspaceTabFocus.test.ts` **5 条失败**：点标签进 shell 正是靠这个 rAF。守卫破坏了产品行为，回退。

### 真正的原因

这条用例在**没有先让标签栏拥有焦点**的情况下，直接 `tabElement("a").focus()`，然后又按 F2。可应用支持的前置状态是「标签栏拥有键盘」（F6 交给它）：此时 `tabFocusTarget === "strip"`，终端的自动聚焦根本不会排队。用例跳过了这一步，终端迟到的 rAF 就会把焦点抢回 shell——这是**用例制造的状态**，不是读者会走到的路径（点标签本来就应该进 shell，单测就是这么要求的）。

### 修法

用例先 `setActive("a", "strip")`，再 `focus()`，并断言焦点确实在标签上，然后才按 F2。断言焦点是关键：如果哪天产品真的从键盘焦点上抢走标签，它会立刻失败，而不是变成一个偶发。

### 证据与限度

- 单测 `WorkspaceTabFocus.test.ts` 12/12 通过（证明点标签进 shell 的行为未变）；
- `tabRename.browser.test.ts` 连跑 3 次全绿；
- 全量浏览器连续 2 次全绿（290 用例）。

仍然只把「全量连续多轮不再出现」当作根除的证据；本轮做到的是：**根因定位到用例前提，并用一条显式的焦点断言把这类偶发变成可诊断的失败**。
