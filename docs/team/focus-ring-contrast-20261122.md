# 焦点环对比度（2026-11-22 第 6 轮）

第 3 轮证明了"每个焦点停靠点都有可见变化"。但变化不等于**看得见**：环的颜色若与它所在的表面相同（1:1），所有计算属性都会变，键盘用户却什么也看不到。本轮补上颜色这一半。

## 一、新增收集器

`focusRingContrastIssues(root)`（[uiAudit.ts](../../src/uiAudit.ts)）对每个真实焦点停靠点：

1. 聚焦，读 `outline-width/style/color`；
2. 按 `outline-offset` 的符号选背景：负偏移（内嵌）取元素自身表面，正偏移取父级表面（`surfaceBehind` 会合成祖先背景）；
3. 计算对比度，低于 **3:1**（WCAG 1.4.11 非文本对比度）即报缺陷。

**只测 outline，且不确定就计数**：软阴影环可能是内嵌、扩散、多层或光晕，重建它的"实际颜色"只是猜测；非 outline 指示器与渐变背景一律计入 `indeterminate`，绝不当作通过。这与第 1 轮"不确定就标 indeterminate"的政策一致。

## 二、覆盖

| 表面 | 断言 |
| --- | --- |
| shell（20 个停靠点） | 有变化 + 环 ≥3:1 |
| 新建会话 / 显示设置 | 同上 |
| 设置索引（View 菜单） | 同上，≥12 个停靠点 |
| 键盘快捷键 | 同上，≥10 个停靠点 |

`sweepFocusStops` 把两件事合成一个断言：一个对话框"通过"现在意味着**既换了样式、且环自己看得见**。

## 三、结果

- 现有界面**没有**环对比度缺陷：`--accent` 在四种主题的对话框表面上都超过 3:1。本轮交付的是回归门禁，不是缺陷修复——这一点如实记录。
- 负向控制证明门禁可失败：把对话框按钮的 `outline-color` 设为 `--bg-menu`（即表面色）后，收集器必须报出缺陷；该用例通过。
- 单元 4 条：21:1 通过、1:1 报错、非 outline 计入不确定、`tabIndex<0` 跳过。

## 五、边界

- box-shadow / 原生平台焦点环、渐变表面 -> `indeterminate`（报告里有数量，不是静默通过）。
- 只覆盖 Chromium；WebView2 的原生控件环形态未验。
- 未测量"环与相邻控件的间距"——那属于 SC 2.5.8 的目标间距，已由尺寸收集器覆盖。
